# Security and privacy requirements

Threat model and implementation contract. Phase 1 implements and tests Argon2id, opaque sessions, session-bound CSRF, role/ownership enforcement, durable rate limits, input/error redaction, concurrency checks and limited DB privileges. Phase 4 implements and tests private bounded uploads, review/restriction concurrency, idempotency, analytics authorization and stream admission. Phase 5 implements safe asset registration, private jobs and a restricted inference worker; trained model resources and production deployment controls remain unresolved. Protect credentials, user preferences, private report evidence, authoritative infrastructure, and audit integrity. Threats include anonymous abuse, another normal user, a compromised account, hostile uploads, stale admin clients, and accidental operator configuration errors.

## Authentication and authorization

Use Argon2id via a maintained library, random salts, and calibrated parameters meeting current OWASP guidance (minimum baseline memory 19 MiB, iterations 2, parallelism 1; measure login throughput and memory). Passwords 12–128 characters; no truncation; reject oversized bodies before hashing. Login errors do not distinguish missing users from bad passwords; use a dummy hash verification for unknown users. Registration duplicate errors remain an explicit usability tradeoff and are rate limited.

Create a 256-bit random opaque session token and store only its SHA-256 hash. Derive the session-bound CSRF token as base64url HMAC-SHA256 of `csrf-v1:` plus the raw session token, using a separate random server CSRF secret. The server can reproduce this from the request cookie without storing recoverable session secrets or invalidating other tabs on every GET. Validate the supplied header in constant time against this value after verifying the session. HttpOnly session cookie: Secure in production, SameSite=Lax, Path=/, no Domain; use `__Host-pathable_session` in production and a distinct non-prefixed localhost development cookie. Rotate session (therefore CSRF) on login/privilege change, revoke old session, enforce idle and absolute expiry, and check user.active/auth_version/role server-side each request. Session view returns the derived CSRF token to same-origin JavaScript with no-store; tokens are never placed in URLs or localStorage. GET /auth/session does not rotate an existing session. Login/logout responses provide the new state; another tab with old state refreshes session on an authentication/CSRF error before an explicit retry.

Require the session-bound CSRF token and exact Origin allowlist for every state-changing method, including login, register, upload and logout. Reject absent Origin for browser write endpoints except a documented authenticated nonbrowser route that still supplies the token. The Phase 3 public `POST /routes/calculate` is a read-only calculation with an explicit complete profile; it requires neither login nor CSRF and does not persist route history or edit user preferences/infrastructure. Its method carries bounded structured input; durable rate-limit buckets and observation-expiry maintenance still apply. Development uses Vite `/api` proxy to keep the browser same-origin. Production reverse proxy serves UI/API on one origin; do not combine wildcard CORS with credentials. CSP, HSTS over TLS, nosniff, frame-ancestors, safe referrer policy and output escaping are deployment/UI gates. Treat report descriptions as plain text, never unsanitized HTML.

Authorization matrix: public users read curated campus data/calculate routes; authenticated users manage their own profile/saved destinations/reports/evidence; admins review reports, change infrastructure and see audit/analytics. A user cannot set role, reporter, reviewer, status, or graph version. Object ownership is checked in DB queries, including evidence, job and prediction IDs. Guessing another user's ID yields 404. Prefer a one-time local admin-creation CLI prompting securely in Phase 1; no default admin password and no public role-promotion endpoint. An admin does not automatically bypass version checks or evidence retention rules.

Initial per-identity limits: login 5/minute plus 30/hour per keyed IP/account bucket; route 60/minute per authenticated user or keyed IP; report 10/hour per user; upload 20/hour per user plus storage quota; SSE max 3 connections/client identity. Values are tunable defaults, not proven capacity. Use DB-backed atomic buckets to avoid per-process bypass; rate-limit dependency failure fails closed for login/write endpoints. Cap anonymous session issuance and expire unused sessions. Only trust forwarded IP/host from configured reverse proxies.

## Upload and ML boundary

Only JPEG and PNG; max 10 MiB encoded, max 20 million decoded pixels, max 3 processing/ready images per report, 100 MiB normalized storage per user. Validate declared MIME, signature, decoder output and actual dimensions; reject SVG, archives, animations, malformed/truncated files and unsupported formats. Bound request streaming even with missing/false Content-Length. Decode with maintained Pillow in a resource-limited worker; decompression-bomb warnings are failures. Normalize orientation, strip EXIF/GPS, and re-encode into controlled storage. No shell interpolation, original filenames in paths, arbitrary URLs, or remote-image fetching.

Write temporary private files using generated IDs, atomic final rename, and DB evidence state transitions. A crash leaves a non-ready row/file eligible for cleanup, never a public unsafe object. Enforce quota with report locks/reservations so concurrent uploads cannot exceed it. Separate storage adapter allows local private volume first and private object storage later. File reads pass owner/admin authorization and set private/no-store headers. Upload directory is not a static mount. Scan/retention policies can be strengthened before public release; normalization alone is not a malware safety claim.

Inference gets only validated ready images and pinned verified model assets. PyTorch weight formats may deserialize code; use safe tensor formats or supported weights_only loading, pinned checksums, and trusted sources. No uploaded model/code execution. Untrusted image text is data, not instructions. A prediction cannot write edge restrictions, graph state, or admin_actions as a reviewer. Admin acceptance of a suggestion remains distinct from verifying a report.

## Operations and privacy

No production secrets in Git, examples, logs, URLs or architecture docs. Secure environment settings provide DB password, CSRF secret and rate-limit hashing key during Phase 1. Cloud proxy-bound credentials may not function as raw local DB passwords; use the platform's supported runtime variable mechanism or local untracked development configuration as appropriate. Inspect existing names/presence before requesting new bindings. Do not ask users to paste secrets in chat.

Use separate migration/app DB roles; enforce append-only audit/history and transaction constraints. Only the table owner may prune graph events older than seven days; no event updates or recent deletes are allowed, and runtime UPDATE/DELETE remains revoked. Backups include database and evidence references; restore drills verify consistency. Keep coordinates/preferences out of routine logs. Do not persist route histories by default. Minimal identity is email/display name; no diagnosis, disability proof or continuous GPS tracking.

Default retention proposal for controlled demonstrations: anonymous sessions 30 minutes, signed-in sessions bounded by TTL, rate buckets <=24h, idempotency 24h, graph replay 7 days, failed upload temp files <=24h. Reporter evidence stays while active review requires it; deletion/account-export/long-term audit retention policy must be settled before public use. Synthetic fixtures contain no real personal data. Dependency/signature/TLS verification must stay enabled; failed verification is a blocker, never a flag to bypass.

## Negative tests required

Phase 1: auth/session rotation/revocation, expiry, CSRF/Origin, unauthorized roles and field injection, cross-user access, duplicate registration race, CAS and audit rollback. Phase 4: upload limits/signatures/path traversal, unauthorized evidence access, concurrent quotas, review conflicts, idempotency and two-report closure preservation. Phase 5: failed/missing inference cannot mutate availability. Phase 6: repeat these through the real frontend, test proxy/header configuration and dependency failures. Unexecuted controls must not be described as secure in release notes.

Phase 4 uses a fresh user share lock to recheck active role/auth_version in reporting and evidence transactions, after initial HTTP authentication. User/report locks reserve quota before decoding outside the DB connection. Review snapshots preserve expected versions and drafts on conflict. Login/logout cancel/remove private report/analytics/audit client queries. Final negative/concurrency/runtime and real browser results are in [Phase 4 evidence](PHASE4_TEST_EVIDENCE.md). Worker limits and normalization reduce risk; they do not establish a general malware sandbox or complete public-release security review.

Phase 5 permits only fixed classifier code and hash-matching safetensors state dictionaries, not pickle, arbitrary paths/URLs or executable uploaded models. The CPU child receives a sanitized environment without inherited credentials and has memory/CPU/wall limits; this is not a general sandbox. Private jobs/predictions retain owner/admin scopes. The actual worker role cannot edit graph/restrictions, evidence, models or review status. A shared content advisory lock prevents late publication after evidence deletion. Prediction acceptance appends annotation audit only; real DB/browser critical F passes with explicitly marked synthetic doubles. Registration rejects fixtures, and unavailable ML never substitutes labels or metrics. Long-term asset privacy/restoration and production worker monitoring remain release gates.

## Phase 6 review

A shared transaction-level authorization refresh now protects infrastructure mutations as well as report/prediction review. It refreshes active status, auth version and required role under a user-row lock before locking the graph. Revocation committed between HTTP authentication and the mutation rejects the edit without graph/audit/event changes.

Evidence reservations take an exclusive user lock for both fresh authorization and per-user quota serialization; publication rechecks after decoding outside the DB transaction. If the account was revoked during decoding, the reservation becomes rejected, no final image is published and temporary files are removed. Deletion also refreshes authorization before changing state or unlinking content. Existing evidence remains private and ready when a revoked deletion is refused.

Non-ASCII CSRF headers receive the normal 403 response. Early 413/415 request-boundary responses retain no-store, nosniff and a matching request ID. Real browser checks exercise the same-origin proxy, CSRF/Origin rejection, session rotation/HttpOnly/SameSite, cross-user report/prediction denial, ordinary-user review denial, plain-text rendering and logout access denial. This localhost proxy validation does not verify a production TLS/reverse-proxy deployment.

Package advisory snapshots cover the locked Python and npm environments; direct-wheel PyTorch is checked separately by its upstream version. Advisory absence is not proof of absence of vulnerabilities. OS/container scanning, CSP/HSTS/frame policy under production TLS, proxy trust, capacity and backup restoration remain Phase 7 release gates.

## Phase 7 release candidate

Pinned offline builds exclude private configuration and weights. Non-root/read-only API/web use private host mounts; API receives no owner password, while explicit operator containers perform migrations/grants/maintenance. Production HTTPS headers/host cookie and unbuffered SSE were checked through Nginx and the actual compiled UI. Anonymous rate limits currently aggregate at the proxy because forwarded identity remains untrusted; public admission/capacity requires separate review. Coordinated snapshots quiesce writes and restore transactionally into pristine targets with file membership/hash/path validation. Backups contain private data and need trusted-operator handling and encrypted off-host retention. Local certificate fixtures are explicitly trusted/pinned; no package TLS/hash check is disabled. See [runbook](RELEASE_RUNBOOK.md) and [Phase 7 evidence](PHASE7_TEST_EVIDENCE.md) for verified scope and unrun public-release controls.

## Phase 8 failure and recovery review

Malformed cursor field types are rejected as 400 before UUID parsing. All structured failures, including exceptions handled outside application middleware, carry no-store/nosniff and a matching request ID; injected failures also prove that pending account edits roll back and internal diagnostic text stays private. Complete backup metadata is validated before contacting the restore target. Recovery stages private files under the configured runtime UID/GID; mismatched unprivileged operators are refused before import. Owner, application and worker role names must be distinct. Startup helpers wait for the expected process command before recording ownership and continue to refuse signaling mismatched identities. These repairs strengthen error handling and local recovery, while the public-release limits above remain. See the [final audit](FINAL_ENGINEERING_AUDIT.md).
